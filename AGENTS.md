# Galaxy XR: persistent device-safety rules

User instruction recorded on 2026-10-10. Applies to all work in this workspace involving the Galaxy XR headset.

- Highest priority: the headset must remain stable and bootable after a full reboot or power cycle. Achieving an experimental feature is secondary.
- Preserve original files on the headset. Do not edit, overwrite, or delete originals to implement a modification. Prefer temporary runtime substitutions (such as bind mounts with replacement files stored separately), in-memory changes, or other reversible methods consistent with these safety rules.
- Do not directly write, erase, flash, or patch firmware partitions, boot images, Verified Boot metadata, bootloaders, partition tables, low-level firmware, or device-specific calibration/identity storage. This includes both slots and logical partitions within super. Do not disable Verified Boot by modifying on-disk images.
- Temporary root is not a rollback mechanism for persistent writes. Treat changes to /data, module installers, and root scripts as potentially persistent and capable of breaking startup; inspect their effects before use. A “systemless” label is not sufficient evidence of safety.
- For system components, keep experimental modifications out of automatic startup. Prefer manually activated changes that disappear on a full reboot. Do not enable root/module/patch autostart if doing so could reapply a failing system modification after reboot. See the non-system application exception below.
- Keep DFRoot read-only partition protection enabled where available; do not rely on it as the sole safeguard.
- Before applying a headset modification, establish what it changes, whether any writes persist, and how a full reboot returns the headset to a working baseline. If that cannot be established, do not apply it; explain the uncertainty and find a safer approach.
- These rules concern modifications to the headset, not ordinary edits to local source code or build artifacts in this workspace.
- Non-system application exception, authorized by the user on 2026-10-10: modifications confined to a non-system application (such as Steam Link) do not require manual activation. Automatic application when that app starts is allowed; do not ask for confirmation solely because activation is automatic. This supersedes the manual-only/no-reapplication requirements for this scope. Establish that the mechanism cannot compromise headset boot or system services and provide a way to disable it independently of the target app. If it reapplies after reboot, do not describe reboot alone as rollback. This exception does not authorize system-service or firmware changes, destructive writes, or unrelated persistent changes; the remaining device-safety rules and the parent AGENTS.md still apply.
- Build and deployment workflow, updated by the user on 2026-10-11: for future headset patch/module work, always prepare two build variants: a manually activated test variant with no autostart, and an automatic variant. Test the manual variant first. Install or enable the automatic variant only after testing and an explicit user request and authorization for that variant. A positive test report alone is not authorization to install or enable autostart. This supersedes the earlier blanket permission to automatically deploy non-system app modifications; their technical scope remains allowed subject to this workflow and all device-safety rules. Preparing the automatic artifact locally does not authorize its installation or activation.
